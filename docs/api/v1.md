# Finisher Legacy API v1

**Estado: ESTABLE.** Cierre de la ronda de hardening de backend/API
(consolidation brief §49) — sin bloqueantes conocidos en el contrato
documentado aquí. Cambios futuros son aditivos (nuevos endpoints/campos
opcionales); un cambio incompatible requeriría una v2.

Base URL: `/api/v1`

El contrato que consumirán la app iOS/Android, otros sitios de Finisher Legacy, y — desde Slice 6 — un futuro Desktop/Mobile para el personal operativo (Event Ops). Cada endpoint reutiliza los mismos Actions/Services/Queries/Policies/Form Requests que la web Inertia — nunca hay lógica de negocio duplicada entre transportes. Ver `docs/api/use-case-matrix.md` para el inventario completo de qué caso de uso vive en qué transporte.

Este documento cubre el **API general** (auth, medallas, eventos, Event Ops, integraciones). El **Device API** (`/api/v1/devices*`, `/api/v1/device*`, `/api/v1/production/*`) tiene su propio contrato, ya documentado en `docs/device-api/v1.md` — más abajo solo se referencia, no se repite.

## Autenticación

Autenticación por token vía [Laravel Sanctum](https://laravel.com/docs/sanctum) (tokens personales, no cookies de sesión). Cada request autenticado debe incluir:

```
Authorization: Bearer {token}
```

Los tokens no expiran automáticamente (configurable en `config/sanctum.php`). El cliente es responsable de invalidarlos vía `POST /auth/logout` cuando el usuario cierra sesión. Un token de `User` nunca autentica una ruta de Device API y viceversa (`App\Http\Middleware\EnsureUserToken` / `EnsureProductionDeviceToken`) — ver `docs/adr/0002-device-production-api.md`.

## Formato de respuesta

**Éxito (recurso único / acción):**

```json
{
  "data": {},
  "message": "Mensaje opcional en español, o null",
  "meta": { "request_id": "..." }
}
```

**Éxito (listas paginadas):** formato estándar de Laravel API Resources — nunca envuelto dos veces.

```json
{
  "data": [],
  "links": { "first": "...", "last": "...", "prev": null, "next": null },
  "meta": { "current_page": 1, "last_page": 3, "per_page": 20, "total": 45 }
}
```

## Errores (Slice 6 — unificado)

**Todo error que no sea de validación** — 401/403/404/409/429/500 — usa el mismo sobre en cualquier ruta bajo `/api/v1/*` (Device API incluido, con su propio catálogo de códigos):

```json
{
  "error": { "code": "NOT_FOUND", "message": "Recurso no encontrado.", "details": {} },
  "request_id": "..."
}
```

`App\Support\Api\ApiExceptionRenderer` es el único lugar que hace esta conversión (Domain Exception Mapper) — ningún controller tiene su propio try/catch a JSON. Cualquier excepción que extienda `App\Exceptions\Api\ApiException` se renderiza automáticamente con su propio código/status (p. ej. `App\Exceptions\PlateAlreadyExistsException` → 409 `PLATE_ALREADY_EXISTS`).

**Decisión deliberada — validación (422) NO se unifica**, se deja el formato estándar de Laravel:

```json
{
  "message": "Los datos proporcionados no son válidos.",
  "errors": { "email": ["El campo email es obligatorio."] }
}
```

Cambiarlo habría roto el manejo de validación de cualquier cliente existente sin beneficio real — es ya una forma bien conocida y normalizada (§49 del prompt Slice 6 permite explícitamente esta elección).

| Status | Código (`error.code`) | Significado |
|---|---|---|
| 200/201/202/204 | — | Éxito |
| 401 | `UNAUTHENTICATED` | Token ausente/inválido |
| 403 | `FORBIDDEN` | Autenticado pero sin permiso |
| 404 | `NOT_FOUND` | No encontrado |
| 409 | `CONFLICT` (o un código específico, p. ej. `PLATE_ALREADY_EXISTS`) | Conflicto |
| 422 | *(formato Laravel estándar, ver arriba)* | Validación fallida |
| 429 | `TOO_MANY_REQUESTS` | Límite de solicitudes excedido |
| 500 | `INTERNAL_ERROR` | Error interno — nunca expone stack trace |
| 422/409/502/501 | Códigos de ecosistema comercial (ver `App\Enums\ApiErrorCode`): `PRODUCT_OUT_OF_STOCK`, `PRICE_NOT_AVAILABLE`, `ORDER_NOT_PAYABLE`, `ORDER_EXPIRED`, `PAYMENT_AMOUNT_MISMATCH`, `PAYMENT_ALREADY_RECORDED`, `LEGACY_PLATE_NOT_PAID`, `LEGACY_PLATE_ALREADY_EXISTS`, `LEGACY_PLATE_EVENT_REQUIRED`, `LEGACY_PLATE_MODEL_REQUIRED`, `LEGACY_PLATE_MODEL_UNAVAILABLE`, `LEGACY_PLATE_QUANTITY_INVALID`, `CART_EVENT_MISMATCH`, `PRICE_CURRENCY_MISMATCH`, `MEDIA_LIMIT_REACHED`, `MEDIA_TOO_LARGE`, `ASSET_ALREADY_CLAIMED`, `EVENT_DATA_SOURCE_NOT_CONFIGURED`, `PROVIDER_CONNECTION_FAILED`, `COUPON_NOT_APPLICABLE`, `SOCIAL_ACTION_NOT_ALLOWED`, `MOMENT_REFERENCE_INVALID`, `SOCIAL_AUTH_UNAVAILABLE`, `SOCIAL_AUTH_INVALID_TOKEN` | Ver `docs/architecture/commerce.md` |

## Request ID

Toda respuesta bajo `/api/*` trae un header `X-Request-ID` — reutiliza el que mande el cliente (`X-Request-ID` en el request) o genera un UUID. Útil para correlacionar logs con soporte a un futuro Desktop/Mobile (`App\Http\Middleware\AssignRequestId`). También aparece en `meta.request_id` (éxito) y `error.request_id`... (dentro del sobre de error, como `request_id` top-level).

## Idempotencia

Escrituras críticas aceptan un header `Idempotency-Key` opcional — una segunda solicitud con la misma clave repite la respuesta original en vez de re-ejecutar la acción:

- Device API: ya existente desde Slice 1/2 (`App\Http\Middleware\EnsureIdempotencyKey`, tabla `device_idempotency_keys`).
- API general (`event-ops/participants/{id}/plate` por ahora): `App\Http\Middleware\EnsureApiIdempotencyKey`, tabla `api_idempotency_keys` — mismo patrón, generalizado a cualquier actor Sanctum (`User` o `ProductionDevice`), nunca dos implementaciones incompatibles.

## Identificadores públicos

Las URLs nunca dependen de IDs incrementales predecibles cuando el recurso es sensible o público:

- **Medallas**: `uuid` (no el `id` autoincremental).
- **Legacy Code**: `code` (p. ej. `Q8K2MX7P`), atemporal.
- **Eventos**: `slug`.
- **Perfiles**: `username`.

IDs incrementales siguen usándose para recursos internos/operativos (`EventEdition`, `EventParticipant`, `ExternalSyncRun`, `ProductionJob`) — solo alcanzables con permiso de staff, no navegación pública.

## Fechas

ISO 8601 para timestamps. Fechas sin hora (`event_date`) en `YYYY-MM-DD`. Los endpoints de Event Ops devuelven varios timestamps como texto relativo (`diffForHumans()`, p. ej. "hace 4 segundos") en vez de ISO — igual que la web Inertia de la que reutilizan el mismo Resource, para no tener dos formatos de fecha para la misma pantalla.

## CORS

`config/cors.php` — sin orígenes permitidos por defecto (`FINISHER_CORS_ALLOWED_ORIGINS`, lista separada por comas). Nunca `*` combinado con `supports_credentials: true`. Sanctum token auth no depende de cookies para `/api/v1/*`, así que CORS solo importa el día que exista un cliente JS en otro origen.

## PII (Slice 6 audit)

Ningún endpoint de Event Ops/Device API devuelve `email`, `phone`, o `birth_date` de un participante — ni en búsqueda ni en detalle. El Device API ya cumplía esto desde Slice 1/2 (auditado, sin cambios necesarios); Event Ops (Slice 6, nuevo) se diseñó así desde el inicio.

## Versión

`GET /health` y `GET /device/bootstrap` devuelven `api_version` (`config('finisher.api_version')`, hoy `"1.0"`) y `minimum_supported_client_version` (nullable, sin aplicar todavía — preparado para cuando exista un cliente real que rechazar). Un bump de `api_version` implica un cambio incompatible; añadir un endpoint nunca lo requiere.

## Auth

### `POST /auth/register`

Crea un usuario, le asigna el rol `athlete`, emite su Legacy ID y un token de API. Misma acción (`App\Actions\Fortify\CreateNewUser`) que el registro web.

### `POST /auth/login`

**Body:** `email`, `password`. **200** → `{ data: { user, token } }`.

### `POST /auth/logout` 🔒

Revoca el token actual.

### `GET /me` 🔒

Devuelve el usuario autenticado — `athlete` (resumen mínimo, si está vinculado) y `permissions` (nombres de permiso de `App\Support\PermissionCatalog`, nunca inferidos de un nombre de rol).

### `POST /auth/forgot-password` · `POST /auth/reset-password`

Mismo broker, correo y página web de reset que Fortify. `forgot-password {email}` siempre responde igual (sin enumerar cuentas). `reset-password {token, email, password, password_confirmation}` cambia la contraseña y **revoca todos los tokens**. Throttle `password-reset`.

### `POST /auth/social/{google|apple}`

`{id_token, nonce?, given_name?, family_name?}` — el ID token nativo se verifica contra el JWKS del proveedor (`App\Services\Auth\IdTokenVerifier`: firma RS256, `iss`, `aud` ∈ `finisher.social_auth.*.client_ids`, `exp`, `nonce`). Vincula por `provider + sub` (`user_social_accounts`), o por correo **verificado** a una cuenta existente, o crea una nueva (rol athlete, Legacy ID, Athlete). Emite el mismo token Sanctum que login → `{user, token, created}`. Apple sin correo → correo placeholder no enrutable. Sin client ids → `422 SOCIAL_AUTH_UNAVAILABLE`; token inválido → `422 SOCIAL_AUTH_INVALID_TOKEN`.

### `DELETE /me/account` 🔒

`{password}` (o `{confirmation: "ELIMINAR"}` si la cuenta tiene login social). Revoca tokens, borra perfil/fotos/momentos/comentarios/reacciones/follows/bloqueos/push devices/cuentas sociales, anonimiza nombre/correo/teléfono, deja privadas las medallas personales, desvincula el Athlete (los resultados oficiales y pedidos se conservan) y hace soft-delete del User. `App\Actions\Account\DeleteAccount`.

## Event Ops API 🔒 (Slice 6, nuevo)

Requiere permiso `operator.access` (el mismo que la web `/operator`). Ver `docs/adr/0006-event-operations.md` y `docs/api/use-case-matrix.md`.

### `GET /event-ops/{eventEdition}`

Dashboard operativo — `App\Queries\Operations\GetEventOperationsDashboard`, misma Query que la web. `data.readiness`, `data.metrics`, `data.production`, `data.stations`, `data.provider`.

### `GET /event-ops/{eventEdition}/participants/search?q=`

Búsqueda por dorsal/nombre — `App\Queries\Operations\SearchEventParticipants`, misma Query/prioridad (dorsal exacto → prefijo → id externo → nombre) que la web. Máximo 20 resultados. Nunca PII.

### `GET /event-ops/participants/{eventParticipant}`

Ficha completa: resultado + splits, resumen mínimo de Athlete, placa existente, elegibilidad (`App\Services\PlateEligibilityService`, Slice 4, reutilizado).

### `POST /event-ops/participants/{eventParticipant}/plate`

Genera la placa integrada — `App\Services\PlateGenerationService::generateIntegrated()`, el mismo Use Case que Event Ops web. **201** con la placa creada. **409** `PLATE_ALREADY_EXISTS` en un segundo intento — usa `Idempotency-Key` para que un reintento de red replique la respuesta en vez de fallar.

## Store — catálogo, carrito, checkout, pedidos, pagos (ecosistema comercial)

Ver `docs/architecture/commerce.md` para el detalle de dominio. Login
requerido para todo lo de carrito en adelante (brief §198).

### `GET /store/products` — público

Paginado. Filtros: `category` (slug), `type`, `q` (nombre/marca), `sort=newest|name`. `meta.categories` lista las categorías con productos a la venta (`{name, slug}`). Cada producto trae `in_stock` y `category_slug`. Nunca stock exacto —
`in_stock` es booleano (brief §176-§177).

### `GET /store/products/{slug}` — público

Detalle + variantes activas.

### `GET /cart` 🔒 · `POST /cart/items` 🔒 · `PATCH /cart/items/{item}` 🔒 · `DELETE /cart/items/{item}` 🔒

Un carrito por usuario autenticado (brief §55/§198). `POST /cart/items` identifica la variante por **`product_variant_uuid`** (público; `product_variant_id` sigue aceptándose por compatibilidad) y la Legacy Plate por `legacy_plate_model_uuid`/`_id`. El carrito **no** es
fuente de verdad de precio. `CartResource` incluye `subtotal_minor`,
`discount_minor` (0 sin cupón), `total_minor` y `coupon` (`{code, name}`
o `null`) — un preview del descuento, nunca autoritativo (ver checkout).

### `POST /cart/coupon` 🔒 · `DELETE /cart/coupon` 🔒

`App\Actions\Commerce\ApplyCouponToCart`/`RemoveCouponFromCart` —
`{code}` en el body. Rechaza con **422** `COUPON_NOT_APPLICABLE` y
`details.reason` (`not_found`/`inactive`/`not_started`/`expired`/
`usage_limit_reached`/`per_user_limit_reached`/`minimum_order_not_met`/
`currency_mismatch`) si el código no aplica. Esta validación es solo
UX — `POST /checkout` siempre revalida server-side (ver
`docs/architecture/commerce.md#cupones`).

### `POST /checkout` 🔒

`App\Actions\Commerce\CheckoutCart` — recalcula precio/stock/totales
server-side, crea `Order`+`OrderItem`s (y `LegacyPlateEntitlement` si
aplica). Soporta `Idempotency-Key`. **201** con la Order creada.

### `GET /orders` 🔒 · `GET /orders/{uuid}` 🔒

Solo las Orders del usuario autenticado. `GET /orders` usa paginación estándar `{data, links, meta}`. Cada Order incluye `payment_state` (pending|processing|paid|failed|cancelled|refunded), `payable`, `expires_at` y `payment` (último intento).

### `POST /orders/{uuid}/payments/online` 🔒

Inicia un pago online. Body opcional `{provider: "stripe"|"openpay"}`; sin él, `finisher.payments.api_gateway` (stripe). Stripe devuelve `client_payload: {client_secret, publishable_key, merchant_display_name}` para PaymentSheet. Si ya hay un intento de Stripe en curso, **reanuda el mismo PaymentIntent** (nunca un segundo cargo). **501** si el gateway no está configurado. Nunca devuelve una llave secreta.

### `POST /orders/{uuid}/payments/sync` 🔒

Consulta a Stripe server-to-server el estado real del último intento y lo aplica por el mismo camino que el webhook (`ProcessPaymentWebhook`). Devuelve la Order actualizada. El cliente nunca marca un pago como pagado.

### `POST /admin/orders/{uuid}/payments/manual` 🔒

Requiere `payments.record_manual`. Registra efectivo/terminal — monto
exacto obligatorio en Fase 1.

### `GET /legacy-plate-models` — público

Solo modelos activos, campos app-safe (sin coordenadas internas de
layout) — ver `docs/architecture/legacy-plate-v2.md`.

### `GET /gear/{code}` — público, sin PII

Lookup de un `AthleteOwnedProduct` por `asset_code`.

### `GET /me/gear` 🔒 · `POST /gear/{code}/claim` 🔒

Digital Closet del Athlete autenticado y reclamo de un asset sin dueño.

### `GET /me/events` 🔒

Reutiliza `App\Queries\Athletes\GetAthleteHistory` — mismo read model que
el admin.

### `GET|POST /me/events/{participant}/media` 🔒 · `POST .../media/reorder` 🔒 · `PATCH|DELETE /me/media/{uuid}` 🔒

Fotos/video de una participación — límites gratuitos configurables
(`config('finisher.event_media')`), MIME real verificado
(`UploadedFile::getMimeType()`), nunca la extensión del cliente. Videos: `video/mp4`, `video/webm` y `video/quicktime` (.mov de iOS, guardado tal cual; transcodificación = trabajo futuro). `POST .../media/reorder` acepta **`media_uuids[]`** (`media_ids[]` por compatibilidad); un uuid de otra participación → 422.

### `GET /me/events/{participant}/media-entitlement` 🔒

`{images:{used,limit,remaining,max_bytes,allowed_mimes}, videos:{…}, memory_packs_enabled}` — la única fuente de límites para el cliente. Suma `media_entitlements` (Memory Packs) sólo si `FINISHER_MEMORY_PACKS_ENABLED`.

## Notificaciones

### `POST /admin/users/{user}/notifications` 🔒

Requiere `notifications.send`. Equivalente REST del botón "Comunicación"
en Admin (Participante/Atleta) — reutiliza la misma
`App\Actions\Notifications\SendAthleteNotification` que esos controllers
Web, nunca reconstruye `AthleteAlert` por su cuenta (brief §36-§40). Body:
`{type, title, message, action_url?, push?}`. `push: true` solo *solicita*
el envío push — la respuesta siempre incluye `push_available` (si
`PushNotificationGateway::isConfigured()` es real) para que el llamador
sepa honestamente si algo se entregó de verdad o solo quedó como
notificación in-app (brief §31-§35, hoy `NullPushNotificationGateway` →
siempre `false`). Auditado vía `activity()` (remitente, destinatario,
tipo, `push_requested`, timestamp) — nunca el cuerpo del mensaje ni el
push token (brief §42). Rate limit ~30/min por admin
(`throttle:admin-notifications`).

## Lo que falta (deuda conocida, no bloqueante)

- Scopes/abilities granulares por token de `User` (hoy todo token de usuario tiene acceso completo a las rutas de ese usuario — sin caso de uso real todavía que pida menos).
- `OverrideEventResult` como Action explícita separada — hoy la corrección manual de resultados vive dentro de `App\Actions\Integrations\IngestEventResult` (respeta `manual_override_fields`), sin una Action/endpoint dedicado para que un humano la dispare directamente vía API o Web todavía.
- Resultado API de solo-lectura para `EventResult`/splits fuera del contexto de Event Ops (hoy solo se leen dentro de `participants/{id}`).
- OpenPay real, carrito de invitado — ver `docs/architecture/commerce.md` §Deuda conocida. Stripe: SDK real implementado (§Store arriba), sin cuenta/llaves reales todavía. La expiración de reservas ya no es deuda: `App\Actions\Commerce\ExpirePendingOrder` + `finisher:expire-pending-orders` (scheduler, cada 5 min) la cubren.
- Thumbnails/transcoding para event media — ver `docs/architecture/athlete-assets.md` §Deuda conocida.
- Admin CRUD API para `Product`/`ProductVariant`/`LegacyPlateModel` — hoy solo backend (Actions/Models), sin controllers/rutas admin todavía (`OrganizerDataSource` ya tiene API, ver arriba); la Web Admin sigue usando Actions directamente cuando exista esa UI.
- `IncidentController@resolve` (admin Web existente) no migrado a exigir `resolution_type` — la nueva API sí lo exige; la UI Web actual seguiría usando el flujo viejo hasta una pasada de frontend coordinada.
